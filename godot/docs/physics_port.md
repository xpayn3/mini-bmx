# Ride physics: GDScript -> portable C# (2026-11-28)

Branch `claude/physics-porting-c-39765e` (not on `main` until the user says so). `scripts/bike/bike_physics.gd` stays
the source: the C# ride is GENERATED from it, so a physics change is still made in GDScript and generated again.

## Goals
1. **Identical**: same state + input -> the same numbers as `bike_physics.gd`, every member, bit for bit.
2. **Portable**: the ride core (`godot/sim/`) is plain C#, no engine reference: drop it into Unity, a console / Switch /
   mobile build or a server. Only a thin adapter knows Godot. `dev/port/simcheck/` builds it with no Godot at all.
3. **Deterministic everywhere**: its own math (SimMath), its own random numbers (Pcg32) and noise (Noise2S): the same
   answers on x64 / ARM / any compiler.
4. Faster where it counts (measured below).

## Layout
```
godot/sim/                  engine-free core, namespace Runout.Sim (tools/sim_purity.ps1: no engine reference)
  SimMath.cs                sin cos tan atan atan2 asin acos exp log tanh pow exactly as GDScript computes them on PC
  Gd.cs                     GDScript's global functions with Godot's edge cases (maxf, clampf, move_toward, wrapf,
                            smoothstep, roundi, % formatting...) + V2 / V3 = Godot's float32 Vector2 / Vector3
  Pcg32.cs, Noise.cs        Godot's RandomNumberGenerator / FastNoiseLite (simplex smooth, FBm), bit for bit
  Contracts.cs              IGround (what it asks the world), IRideHost (what it tells the game), ISusp, RideParams
                            (Tune values), RideInput, GdDict, SusSetup, SuspMath, Env (test switches)
  BikeSim.gen.cs            THE RIDE: generated from bike_physics.gd by dev/port/gd2cs.py (do not edit)
  BikeSim.Manual.cs         the few functions the translator leaves out (setup, the crash step's core part, probes)
godot/scripts/bike/
  bike_physics.gd           the GDScript ride, unchanged but for `# (cs-hook)` lines: step() hands over to C#, and at
                            its end _cs_out / _cs_in = the state as one packed array (generated by gen_mirror.py)
  BikePhysicsCs.cs          the C# step behind it + the crashed bike / ragdoll step (engine objects, hand ported)
  BikePhysicsCs.gen.cs      the same array slots on the C# side (generated)
  RideBridge.cs             Godot glue: GodotGround (Terrain), GodotRideHost (Game), GodotSusp, engine math, the
                            state mirror used by the lockstep harness
godot/dev/port/             gd2cs.py (translator), gen.sh (generate + build the core alone), gen_mirror.py,
                            host_tap.gd + dev/sim/BikeLockstep.cs (BMX_PHYS=cmp)
```
**After changing bike_physics.gd**: `bash godot/dev/port/gen.sh` (regenerates BikeSim.gen.cs, builds the core with no
Godot) then `python godot/dev/port/gen_mirror.py` (only if members were added / removed), `dotnet build`, and a
lockstep run (below). For Unity: copy `godot/sim/`, write a Unity IGround + IRideHost. Nothing else.

## How the game uses it (the default; BMX_PHYS=gd = the GDScript step, cmp = both compared)
The game keeps holding the GDScript `BikePhysics` (typed as before; everything reads it at full GDScript speed: the
rider pose, audio, HUD, ride log, replay snapshots, the playground's reset). `step()` hands over to `BikePhysicsCs`:
the 436 number / bool / int members cross in one packed array, the C# ride steps, they cross back (+ `crash_pending`,
`_risk`, `_cb_hit`; the Tune values when Tune changes; the crashed-bike body when set). Before each of the game's
callbacks inside a step (effects every tick, events) the state is mirrored to GDScript first and read back after, so
the game sees exactly the mid-step values it saw when GDScript stepped. Every other method (reset_at, get_up,
begin_crash, shift...) stays GDScript: the GDScript object owns the state between steps.
(A first version made the C# object the game's `phys` directly: every GDScript read then crossed into C#, ~0.75 ms a
frame of reads, slower than before. The mirror crosses twice a tick: the pull before the step and the push before
`ride_fx`, which is the step's last statement, so no push is needed after it. pack / unpack are methods of
BikePhysics itself: through another object (`ph.x`) they took twice as long.)
Only the world's own ride steps in C# (`host is Game`): the headless tools (slope_stress, phys_test) keep GDScript.
`CS_DEFAULT` in bike_physics.gd turns the default off.

## Any terrain (user, 2026-11-28: "works on other terrains, e.g. other terrain generators in Unity")
The physics never knows what made the ground; IGround is the whole contract, metres, Y up: `height`, `deck_height`
(no rock / log bumps), `top_height` (drawn), `surface` (0 ground / 1 trail / 2 water / 3 sand), `jump_mask`,
`colliders_near` (plain dictionaries), and `cast(origin, dir, max)` -> RayHit. Any generator can answer these (Unity
Terrain, a mesh + raycasts, voxels). Limit: one height per spot, as today.
**Wallrides / overhangs later (user)**: `cast()` is the general contact query (a height field answers downward casts,
a mesh world any direction). The ported step asks for heights (identical results); riding walls means a contact
model on `cast` + the surface normal (the bike's "up" from the ground instead of world +Y): a physics feature after
the port, the interface won't change.

## How "identical" is checked
- `tools/sim_math_probe.gd`: 400k inputs per function, GDScript vs SimMath. All 0 (table below).
- `tools/sim_rng_probe.gd`: Pcg32 vs RandomNumberGenerator (5 seeds x 200k: rand / randf / randfn) and Noise2S vs
  FastNoiseLite (4 configs x 200k). All 0.
- **Lockstep, `BMX_PHYS=cmp`** (dev): every tick the GDScript ride's state is copied into a C# twin, both step with
  the same input and the same answers from the game (dev/port/host_tap.gd records them), and all 594 members are
  compared bit for bit (`PHYSCMP` lines, `PHYSCMP SUM ... PASS`). Re-copied every tick, so a difference shows in the
  tick it is made. Crashed ticks (the ragdoll) and ticks where something was smashed (the twin, stepping after, sees
  the broken tape / fence) are skipped and counted.
- Free running, the C# mode vs GDScript: the playground suite (24 deterministic runs) diffed line by line.

| function | GDScript on PC | SimMath | mismatches / 400k |
|---|---|---|---|
| sin cos exp log atan2 | x87 (64-bit mantissa, then double; sin / cos reduced with the x87's 66-bit pi) | double-double rounded the x87 way; near-ties (~0.2 %) asked of the engine | 0 |
| pow | x87 (fyl2x / f2xm1) | same; a 256-ulp band (~19 % of calls) asked of the engine | 0 |
| atan asin acos tanh | the same CRT as .NET's Math on Windows | `Platform` hook = .NET Math | 0 |
| tan | neither model | `Platform` hook: the engine | 0 |
Pcg32's randf takes its exponent from the first draw's LEADING zeros; randfn does cos and log in float. FastNoiseLite's
gradient table ends in 8 diagonal pairs. Without the engine hook (another platform) SimMath gives its own double-double
answers: deterministic, within the last bit of GDScript's.

## Speed (seed 4242 follow ride, RTX 3090, no vsync; BMX_PERF=1 = Game's sections, BMX_CSPERF=1 = inside the C# step)
`p_bike_step` per frame: GDScript 0.70-0.71 ms, C# 0.61-0.63 ms (two runs each); the rest of the frame the same.
Inside a C# step (~310-370 us): the ride ~90-135 us, ground queries ~70-125 us (straight to TerrainFieldCs /
RutFieldCs with terrain.gd's arithmetic; rope bridges, the drawn mesh height, colliders and level terrains ask
Terrain), the mirror ~40 us, the game's own callbacks ~120-150 us (`ride_fx` = dust / tracks / sound: GDScript, the
same cost either way). What is left to gain is mostly outside the physics (ride_fx, the terrain field itself).
